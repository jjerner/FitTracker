# 5.7 – Change password / delete account (Profile)

Issue: jjerner/FitTracker#22. HANDOVER.md → Proposed roadmap → section 5, row 5.7 (effort S–M, no other notes).

## Goal

From Profile, a signed-in user can change their password and can permanently delete their account and all their data. Both app stores require in-app account deletion.

## Store rules (why delete is needed)

- **Apple** (App Review Guideline 5.1.1(v)): an app that lets people create an account must let them start deleting it *inside the app*. Turning the account off is not enough.
- **Google Play** (account deletion policy): the same in-app path, **plus** a web link where people can ask for deletion without the app. That link goes in the Play Console Data safety form. It is not part of this change (see Out of scope / Open question 3).

## What exists today

- `AuthProvider` only holds `session`. Signing out (`supabase.auth.signOut()` in Profile) drops the session, and `(tabs)/_layout.tsx` redirects to login. Deleting the account can use the same path.
- `forgot-password.tsx` changes the password with `supabase.auth.updateUser({ password })` after an emailed code. Change password can use the same call, but the user is already signed in.
- Profile (`src/app/(tabs)/profile/index.tsx`) has a "Nutrition Goals" link row (pushes to `profile/goals`) and a red-outlined "Sign Out" button.
- **Cascade check.** Every user table cascades when its `auth.users` row is deleted (`profiles`, `food_log_entries`, `nutrition_goals`, `body_weights`, `workout_templates`, `workout_logs`, `exercises.created_by`, `tracked_exercises`, `saved_meals`, `food_servings`, `favourite_foods`, plus child rows through their parents). **One exception: `foods.created_by` (0002_food.sql line 18) has no `on delete`.** So deleting a user who made a custom food fails with a foreign-key error. The migration below fixes that.

## Deletion: two options compared

| | A. SQL function, called with `rpc` (recommended) | B. Edge Function with the service role key |
|---|---|---|
| What it is | `security definer` function that runs `delete from auth.users where id = auth.uid()` | Deno function that checks the user's token, then calls `auth.admin.deleteUser(id)` |
| New pieces | One migration the user pastes | Supabase CLI deploy, service-role secret, function code, a migration for the FK anyway |
| Safety | Can only delete the caller (`auth.uid()`). `anon` gets no execute right | Same, if the token check is written correctly |
| Extra power | None needed today | Can also delete Storage files (not used yet; photos in 4.3 would need it) |

Pick A. B only pays off once Storage holds user files, and switching later is easy.

## Files to touch

1. **New `supabase/migrations/0017_delete_account.sql`** (the user pastes it):
   ```sql
   -- Custom foods go with their owner (the old FK had no ON DELETE and blocked account deletion).
   alter table public.foods
     drop constraint foods_created_by_fkey,
     add constraint foods_created_by_fkey
       foreign key (created_by) references auth.users(id) on delete cascade;

   -- Lets a signed-in user delete their own account. All their rows cascade.
   create function public.delete_my_account()
   returns void
   language sql
   security definer set search_path = ''
   as $$
     delete from auth.users where id = auth.uid();
   $$;

   revoke execute on function public.delete_my_account() from public, anon;
   grant execute on function public.delete_my_account() to authenticated;
   ```
2. **New `src/app/(tabs)/profile/password.tsx`** ("Change password" screen). Fields: current password and new password (both `LabeledInput password`). On submit:
   - `supabase.auth.signInWithPassword({ email: session.user.email, password: current })`. If it fails, show "Current password is wrong".
   - Then `supabase.auth.updateUser({ password: next })`. Show Supabase's error text if it fails (too short, same as old, etc.).
   - On success: `router.back()`.
   - Signing in fresh also makes the change pass if Supabase's "Secure password change" setting is on.
   - Copy the button, error and loading styles from `forgot-password.tsx`.
3. **`src/app/(tabs)/profile/_layout.tsx`**: add `<Stack.Screen name="password" options={{ title: 'Change password' }} />`.
4. **`src/app/(tabs)/profile/index.tsx`**:
   - Add a "Change password" `Link` row under Settings, the same as the Nutrition Goals row (lock icon: `{ ios: 'lock', android: 'lock', web: 'lock' }`).
   - Add a "Delete account" text button below Sign Out, in `colors.danger`. It asks "Delete your account and all your data? This can't be undone." (`Alert.alert` with Cancel / Delete (destructive); on web use `window.confirm`, the same pattern as `recipe.tsx` line 100.) On confirm:
     - `const { error } = await supabase.rpc('delete_my_account')`
     - If there is an error, show "Could not delete account. Check your connection and try again." and stay on the screen.
     - Otherwise `await supabase.auth.signOut({ scope: 'local' })`. Use `local` because the server sessions are already gone, and a normal sign-out would call the server and might fail. The tabs layout then redirects to login.
     - While it runs, disable the button and show an `ActivityIndicator`.

## Reuse

- `LabeledInput` with `password` (eye toggle) for both password fields.
- `supabase.auth.updateUser({ password })`, as in `forgot-password.tsx`.
- The existing Link row and `signOutButton` styles in Profile.
- The web confirm pattern from `recipe.tsx` (Alert has no buttons on web).
- The redirect to login in `(tabs)/_layout.tsx` when `session` is null. No change to `AuthProvider`.

## Acceptance criteria

- [ ] Profile shows a "Change password" row and a "Delete account" button.
- [ ] Change password with the wrong current password shows an error and changes nothing.
- [ ] Change password with the right current password and a valid new one returns to Profile. Logging out and back in works with the new password and fails with the old one.
- [ ] If Supabase rejects the new password (for example, too short), its message is shown.
- [ ] Delete account → Cancel does nothing.
- [ ] Delete account → confirm sends the user to the login screen. Logging in with that email fails ("Invalid login credentials").
- [ ] After deletion the SQL editor shows no rows for that user id in any user table, including their custom `foods` rows. The shared OFF/SLV foods (`created_by is null`) are untouched.
- [ ] A user with custom foods, custom exercises, saved meals and workouts can be deleted. The FK no longer blocks it.
- [ ] Calling `delete_my_account` while signed out (anon key, no session) is refused.
- [ ] `npx tsc --noEmit` and `npx expo lint` pass.

## Open questions

1. **Delete account confirmation:** is a simple "Delete / Cancel" dialog enough, or must the user type their password (or "DELETE") first? The dialog is smaller. The password step guards against an accidental tap or someone holding an unlocked phone.
2. **Change password:** ask for the current password (spec as written), or only a new password (smaller, but anyone with the unlocked phone can change it)?
3. **Google Play web deletion link:** where should it live (for example, a short GitHub Pages page with a mailto, or the privacy policy page) and who handles the emails? It is needed before Play submission, not for this change. Should it become its own roadmap item?

## Out of scope

- Edge Function / service-role deletion (option B) and deleting Storage files (no Storage in use yet).
- The Google Play web deletion page (Open question 3).
- Change email.
- A grace period or "undo" for deletion. It is instant and permanent.
- Cancelling local reminders and clearing the device cache on delete or sign-out. Sign-out doesn't do this today either. A stale "log your food" reminder only opens the login screen.
- Exporting data before deletion (item 5.5).

## Decisions (PM, 2026-10-18)

1. Lives in the new **Account sub-screen** from S42 (build S42 first). Sign out is a plain row; Delete account is red, at the very bottom.
2. **Delete needs several verifications** (follow UX rules for destructive actions): tapping "Delete account" opens its own screen that explains what gets deleted forever → user re-types their **password** (checked with `signInWithPassword`) → the red "Delete my account" button is disabled until then → a final "Are you sure?" confirm (`window.confirm` on web) → rpc.
3. Change password **asks for the current password** first.
4. Google Play web deletion link is **not** part of this; noted on #35 (store release audit).
