# 1.12 – APK update banner for testers

Source: GitHub issue jjerner/FitTracker#16, HANDOVER.md → Proposed roadmap row 1.12. Labels: `sql`, `apk-build`.

## Goal

When a newer APK exists, Home shows a banner "New version available → Download" that opens the EAS install page. Phones on an old APK stop getting `eas update`s without anyone noticing, and this banner fixes that.

## Design

- A new table `app_releases` has one row per APK build. The user adds the row with SQL after each `eas build`, and the app never writes to it.
- The app reads its own build number with `Application.nativeBuildVersion` from `expo-application`. On Android this is the `versionCode` as a string (e.g. `"7"`), and on web it is `null`.
- Home fetches the newest row (`order by version_code desc limit 1`). If its `version_code` is higher than the app's own build number, Home shows the banner at the top, above the greeting.
- Tapping the banner calls `Linking.openURL(install_url)`.
- When the build number is `null` (web), the query does not run and no banner shows. When the query fails (offline, or the table is missing), no banner shows either. The banner is a nice-to-have, so it never shows an error.
- `eas.json` → `build.preview` gets `"autoIncrement": true`. `cli.appVersionSource` is already `"remote"`, so EAS keeps the counter and bumps `versionCode` on every build. `app.json` has no `android.versionCode`, and none is needed.

## Files to touch

- `supabase/migrations/0017_app_releases.sql` (new). `0016` is taken, so the next free number is `0017`.
  ```sql
  -- One row per APK build; the app shows an update banner when a newer row exists. Rows are added by hand after each eas build.
  create table public.app_releases (
    version_code int primary key,
    install_url text not null,
    notes text,
    created_at timestamptz not null default now()
  );
  alter table public.app_releases enable row level security;
  create policy "Signed-in users can read app releases"
    on public.app_releases for select to authenticated using (true);
  ```
  There is no insert, update or delete policy, so the app cannot change the table. Rows go in through the SQL editor, which runs as the table owner.
- `package.json`: add `expo-application` with `npx expo install expo-application`. It is already in `node_modules` at 57.0.3 because `expo-notifications` depends on it, but the app must not import a package it does not list.
- `eas.json`: add `"autoIncrement": true` to `build.preview`.
- `src/lib/appRelease.ts` (new, about 20 lines):
  - `getLatestRelease(): Promise<{ versionCode: number; installUrl: string; notes: string | null } | null>`. It runs `select('version_code, install_url, notes')`, then `.order('version_code', { ascending: false }).limit(1).maybeSingle()`, and throws on error, the same way as `profile.ts`.
  - A pure function `isNewer(ownBuild: string | null, latest: { versionCode: number } | null): boolean`. It returns false when either value is null or `Number(ownBuild)` is NaN. Otherwise it returns `latest.versionCode > Number(ownBuild)`.
- `src/app/(tabs)/home.tsx`:
  - An inline `useQuery({ queryKey: ['latestRelease'], queryFn: getLatestRelease, enabled: Application.nativeBuildVersion != null })`. Inline queries are already used in `food/search.tsx` and `saved-meals.tsx`.
  - When `isNewer(Application.nativeBuildVersion, data)` is true, render a `Pressable` banner first in the `ScrollView` with the title "New version available → Download" and, if present, `notes` on a second line. Give it `accessibilityRole="link"`. Its `onPress` calls `Linking.openURL(data.installUrl)`.
  - Use the existing theme tokens (`colors.primary` background, `colors.onPrimary` text, `radius.lg`, `spacing`). Do not add a new color.
- `src/lib/__tests__/appRelease.test.ts` (new): tests for `isNewer`.
- `HANDOVER.md`: add a "Release step after each `eas build`" line with the insert template below. Also update the 1.12 roadmap row and the next free migration number (`0018`).
  ```sql
  insert into public.app_releases (version_code, install_url, notes)
  values (<versionCode>, 'https://expo.dev/accounts/jjerner/projects/FitTrack/builds/<build-id>', '<short note>');
  ```
  The `versionCode` is on the EAS build page, or comes from `npx eas-cli build:version:get -p android`.

## Reuse

- `supabase` client and the throw-on-error pattern from `src/lib/profile.ts`.
- `useQuery` from `@tanstack/react-query`, used inline the same way as other screens.
- `Linking` from `react-native`, or `expo-linking` (already installed). Either works for an `https` URL, so pick whichever `home.tsx` already imports most easily.
- Theme tokens from `src/theme.ts`.
- Check the SDK 57 docs before coding (`https://docs.expo.dev/versions/v57.0.0/sdk/application/` and the EAS "app version management" page for `autoIncrement` with `appVersionSource: remote`). The installed types (`node_modules/expo-application/build/Application.d.ts`) say `nativeBuildVersion: string | null`, which is the Android `versionCode` and `null` on web.

## Acceptance criteria

- [ ] `0017_app_releases.sql` creates the table, and signed-in users can `select` from it. An `insert` from the app with the anon key or a user JWT is refused by RLS.
- [ ] `eas.json` preview profile has `"autoIncrement": true`. `expo-application` is listed in `package.json`.
- [ ] On a phone whose build number is lower than the newest row, Home shows the banner, and tapping it opens the `install_url` in the browser.
- [ ] When the build number is equal to or higher than the newest row, or the table is empty, there is no banner.
- [ ] On web there is no banner, no `app_releases` request in the network tab, and no console error.
- [ ] If the table is missing or the request fails, Home looks the same as today and shows no error.
- [ ] TalkBack reads the banner as a link with its text.
- [ ] HANDOVER.md has the release step with the insert template.
- [ ] `npx tsc --noEmit` and `npx expo lint` pass.

## Test plan

- Unit tests (`src/lib/__tests__/appRelease.test.ts`) for `isNewer`:
  - `('5', {versionCode: 6})` → true
  - `('6', {versionCode: 6})` → false
  - `('7', {versionCode: 6})` → false
  - `(null, {versionCode: 6})` → false
  - `('5', null)` → false
  - `('abc', {versionCode: 6})` → false
- Web click-through with the test account from `.env.test.local`, after the SQL is applied: Home loads as before, there is no banner and no `app_releases` request, and the console is clean. The banner itself cannot show on web because `nativeBuildVersion` is `null`.
- Before merging, run `npx expo-fingerprint fingerprint:generate` (or `npx eas-cli fingerprint:compare`) on master and on the branch. This shows whether adding `expo-application` as a direct dependency changes the runtime fingerprint. Report the result (see open question 2).
- Add these to the phone test list in HANDOVER.md, to run after the next APK build:
  1. Install the new APK.
  2. Insert its row. Check there is no banner.
  3. Insert a test row with `version_code` one higher and any `install_url`. Check the banner shows, tapping it opens the link, and TalkBack reads it.
  4. Delete the test row.

## Needs from the user

- Paste `supabase/migrations/0017_app_releases.sql` into the Supabase SQL editor before shipping. The app does not break without the table (no banner shows), but the phone test needs it.
- A new APK build (`eas build --profile preview`, label `apk-build`). The banner ships in that build, and the friends install it by link once.
- After that build, and after every later one, paste the `insert` row (version code plus the build page URL).
- Optional: run `npx eas-cli build:version:get -p android` so the first row uses the right number. The builder can run this too, since it is read-only.

## Open questions

1. Should the banner have a ✕ to hide it (for example until the app restarts)? This spec makes it always visible until the phone is updated, with no dismiss.
2. `expo-application` 57.0.3 is already autolinked into today's APK through `expo-notifications`. If the fingerprint check shows no change, should the banner also ship now via `eas update` to the phones on the current APK, instead of only in the next build? It would stay hidden until a newer row exists.

## Out of scope

- iOS and store builds. Only the `preview` Android profile exists, so there is no per-channel or per-platform column.
- Forcing an update or blocking the app on an old version.
- An in-app APK download or install. The banner only opens the browser.
- Writing rows from the app or a CI hook. Rows are added by hand with SQL.
- Detecting a stale build when the phone is offline.

## Decisions (PM, 2026-10-18)

1. Banner **has a ✕**. Hiding it lasts until the next app start (no storage); it comes back while the APK is still old.
2. If the fingerprint check shows `expo-application` is already in today's APK (runtime unchanged), the banner **also ships via `eas update`** to today's phones. Otherwise it only ships in the next APK.
3. Migration number gets assigned at build time (several items in this batch want 0017).
